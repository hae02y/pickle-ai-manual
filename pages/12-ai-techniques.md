# 12. 웹 조작·음성·기억·예약 작업에 필요한 AI 기술

> 이 장의 모델 구조 설명은 **기능으로부터의 기술적 추론**이다. Pickle이 사용한 특정 모델, 학습 데이터, 프롬프트, 벤치마크는 공개 자료로 확인하지 못했다. 제품에서 확인되는 기능은 [공식 소개](https://pickle.com/help/start/what-is-pickle)와 [작업 안내](https://pickle.com/help/tasks/delegate)를 따로 인용한다.

## 웹 작업: 화면 인식에서 상태 검증까지

공식 안내에 따르면 Pickle은 실제 브라우저에서 웹사이트를 조작한다. 이를 구현하려면 에이전트가 화면 또는 문서 구조를 읽고, 현재 페이지가 어떤 상태인지 판별하며, 클릭·입력·스크롤 후 결과를 다시 확인해야 한다. **컴퓨터 비전 기반 화면 인식인지, DOM/접근성 트리 기반인지, 둘의 혼합인지 Pickle의 내부 방식은 미공개**다.

사용자에게 보이는 화면에는 버튼과 글자가 있지만, 에이전트가 활용할 수 있는 정보는 여러 형태일 수 있다. 화면 이미지를 읽으면 사람 눈에 가까운 배치를 볼 수 있고, 문서 구조를 읽으면 요소의 역할과 이름을 얻을 수 있다. 어느 방식이든 가격이 바뀌거나 버튼이 이동했을 때 **이전 화면을 계속 믿지 않고 다시 관찰하는 능력**이 중요하다. 아래 표는 가능한 기술 선택지를 설명하며, Pickle의 내부 방식을 확인한 표가 아니다.

| 기술 문제 | 일반적인 구현 선택지 | 실패가 드러나는 모습 | 사용자가 줄 수 있는 제약 |
| --- | --- | --- | --- |
| 요소 찾기 | 화면에서 글자와 버튼의 위치를 찾기, 웹페이지의 요소 정보 읽기, 이미지 속 글자 인식 | 같은 이름의 버튼을 잘못 누름 | 사이트와 대상 항목을 특정 |
| 상태 추적 | 직전 행동과 새 화면 비교, 페이지 상태 기록 | 이미 제출한 양식을 다시 제출 | “확정번호가 있으면 재제출하지 마” |
| 계획 수정 | 에러·가격 변경·로그인 만료 감지 | 원래 조건을 놓친 채 다음 단계 진행 | 예산·시간·대체안의 우선순위 명시 |
| 최종 검증 | 예약번호, 주문 내역, 확인 메일 교차 확인 | 완료 메시지는 있으나 외부 상태가 없음 | 결과 증빙을 요청 |

이 표는 Pickle의 소스 명세가 아니라 **웹 작업을 따져 보기 위한 분석 틀**이다. 예를 들어 화면 사진으로 버튼을 찾는 방식과 웹페이지 내부의 버튼 정보를 읽는 방식은 기술적으로 다르다. [공개 자격 증명 소스](https://github.com/pickle-com/credential-enclave/blob/cff16a343bf5bb7953e5b65df6ab3600107e127d/README.md)는 로그인 정보를 사용하는 경계를 설명하지만, Pickle이 버튼을 어떻게 찾는지는 밝히지 않는다. 그러므로 어느 방식이 실제 제품에 쓰인다고 단정할 수 없다.

## 음성: 실시간 대화와 전화의 차이

사용자가 피클과 말로 대화하는 기능과 피클이 외부 업체에 전화를 거는 기능은 구분해야 한다. 앞의 기능에는 말을 글로 바꾸고 대답을 소리로 내는 과정이 필요하다. 전화에는 통화 연결, 상대 말의 해석, 언제 끼어들거나 기다릴지 정하는 과정도 필요하다. **실시간 음성 인식(ASR)**, **대화 모델**, **음성 합성(TTS)**, 차례를 조절하는 기술은 가능한 구성 요소다. Pickle이 어떤 모델을 어떻게 연결했는지는 공개 자료로 확인되지 않는다.

전화 작업의 구조적 위험은 **말의 애매함**이다. 직원이 “가능할 것 같아요”라고 말한 것과 “예약 완료, 번호 1234”는 다르다. 에이전트는 상대의 의도를 해석해야 하므로, 독자는 통화 후 업체 측 예약 내역이나 문자로 확정을 확인해야 한다. 이는 음성 모델의 성능이 좋아도 남는 **외부 세계 검증 문제**다.

전화 결과를 평가할 때는 “통화가 연결됐는가”, “필요한 조건을 정확히 물었는가”, “상대가 확답했는가”, “외부 기록이 남았는가”를 나눠야 한다. 첫 두 항목이 성공해도 예약 완료는 아닐 수 있다. 사용자에게는 통화 요약보다 상대의 확인번호나 문자 같은 후속 기록이 더 강한 증거가 된다.

## 기억: 저장과 검색을 구분하기

[공식 제품 소개](https://pickle.com/help/start/what-is-pickle)는 피클이 사용자 정보와 선호를 기억하고 Bubbles에서 확인·수정·삭제할 수 있다고 설명한다. 기술적으로는 **무엇을 저장할지 결정**, **나중에 관련 기억을 찾기**, **새 정보가 옛 정보와 충돌하면 갱신하기**, **사용자에게 수정·삭제 수단 제공**이라는 별개 문제가 있다. 임베딩 검색, 구조화된 프로필, 요약 기억은 가능한 구현 방식이지만 Pickle이 실제 어느 방식을 쓰는지는 공개되지 않았다.

| 기억의 종류 | 예 | 검증 기준 |
| --- | --- | --- |
| 안정적 선호 | “창가 자리 선호” | 다음 작업에도 적용할지 사용자 확인 |
| 임시 조건 | “이번 주 금요일만 2인” | 작업 종료 후 일반 선호로 굳히지 않기 |
| 민감 정보 | 주소·건강·결제 관련 정보 | 저장 필요성과 공유 범위를 따로 확인 |
| 추론한 정보 | “채식주의자일 것 같다” | 사실처럼 저장하지 않고 질문으로 확인 |

기억은 편의를 주지만, **잘못된 장기 기억이 여러 작업에 반복 적용되는 오류**를 만든다. [06장](https://wikidocs.net/471758)의 정기 점검은 단순 정리 작업이 아니라 데이터 품질 관리다.

## 예약 작업: 스케줄러와 에이전트는 다르다

예약 작업은 정해진 시점에 목표를 다시 실행하는 기능이다. 스케줄러 자체는 AI가 아니며, 실행 시점의 새 이메일·가격·일정을 해석하고 후속 행동을 고르는 부분에 AI가 관여할 수 있다. 조건이 오래되거나 연결 계정 권한이 바뀌면 예상하지 못한 결과가 나올 수 있다. 따라서 **실행 주기, 입력 자료, 허용 행동, 승인 기준, 종료 날짜**를 각각 명시해야 한다. [공식 사용량 안내](https://www.pickle.com/help/credits/usage-credits)에 따르면 예약 작업과 브리핑은 사용량에 영향을 줄 수 있다. 현재 요금·한도는 국가와 계정 화면에서 재확인한다.

## 성능을 평가한다면

제품의 “성공률” 한 숫자보다 아래 지표가 유용하다. 이는 이 책이 제안하는 **평가 설계**이며 Pickle의 공표 성적이 아니다.

| 지표 | 측정 방식 | 왜 필요한가 |
| --- | --- | --- |
| 조건 준수율 | 예산·날짜·인원 등 충족 작업 / 시도 작업 | 그럴듯한 결과와 올바른 결과 구분 |
| 외부 확정률 | 업체·사이트에서 확인된 완료 / 완료라고 보고한 작업 | 보고의 신뢰성 측정 |
| 중복 실행률 | 동일 예약·주문이 두 번 만들어진 비율 | 재시도 위험 측정 |
| 승인 누락률 | 승인이 필요한 행동 중 사전 승인 없는 행동 | 통제 경계 확인 |
| 복구 시간 | 오류 발견부터 안전한 종료·수정까지 걸린 시간 | 실제 업무 적합성 측정 |

특히 **결제와 예약의 중복 실행률**은 평균 응답 속도보다 중요할 수 있다. 독자는 중요한 작업의 결과를 별도 서비스에서 확인하고, 재시도 전 기존 주문 상태를 읽어야 한다.

이 지표를 실제로 비교하려면 먼저 같은 유형의 작업을 여러 번 관찰하고, “성공”의 뜻을 미리 고정해야 한다. 후보 추천의 성공과 결제 완료의 성공을 한 숫자로 합치면 해석이 어려워진다. 각 작업의 **요청 조건, 피클의 보고, 외부 서비스 기록, 사람이 개입한 지점**을 함께 보존해야 원인을 분석할 수 있다.
